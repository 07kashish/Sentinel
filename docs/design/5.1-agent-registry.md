# 5.1 — Agent registry and unregistered-agent detection

**Design proposal for approval · 2026-11-12 · base cd0810e.** Proposal only. Sentinel provides independent, cross-vendor oversight through Observe → Decide → Act → Prove; only deterministic rules decide.

## 1. Model and reuse

**Proposed approach:** add an approval registry alongside observation inventory. Extending `agents` would conflate registration with signature trust; free-text declarations cannot provide identity uniqueness or permission history.

Reuse `domain/inventory.py` / `infrastructure/inventory.py` (`AgentProfile`, `SqlAgentInventory`, observations/edges), identity providers/workload verification, capabilities, `agent_tool_grants`, authorizations, tenant transactions and evidence/Merkle proofs. Inventory classification stays enrollment-based; `agents`/`SqlAgentRegistry` remain signature trust anchors. Registration neither enrolls keys nor grants execution authority. Migration 40 dropped `users`; do not resurrect it or SCIM for ownership.

All keys/foreign keys include tenant; cross-tenant references are refused:

| New table/type | Minimum content and constraints |
|---|---|
| `registered_agents` / `RegisteredAgent` | Generated stable `agent_id`, name, purpose, vendor, **human owner** `{issuer, subject, display_name}`, status `active/suspended/revoked`, revision, timestamps. Owner declares accountability through the tenant's human OIDC issuer, not who acted. Platforms derive from bindings. |
| `agent_platform_identities` / `PlatformIdentity` | ID, agent FK, platform, authority/host, account scope, kind, external ID, display aliases/provenance, optional inventory ID, approved permissions, retirement time. Unique `(tenant, platform, authority, account, kind, external_id)`; immutable, nontransferable keys; retirement preserves history. |
| `agent_registry_records` / `RegistryRecord` | Durable change/observation/gap receipt: ID, tenant-unique idempotency key, source/event identity, timestamps, principal/provenance, before/after snapshot or observation, evaluated revision, digest. Body immutable; mutable delivery/proof fields track publication. Provides history and replay protection. |
| `agent_registry_findings` / `RegistryFinding` | Tenant-unique finding key, rule/version, identity (nullable for coverage gaps), reason/receipt references, evaluated revision, first/last event times and distinct-event count. Historical projection; no open/resolved workflow in 5.1. |

Permissions are exact namespaced `(permission, level, resource_scope)` tuples; empty means none, with no wildcard or inferred implication. Local tool grants stay separate. Inventory joins use explicit bindings; external observations use a hash of the complete typed identity, never display names.

**Migration 41 only:** create these four tables/indexes, append the migration and extend the live-table inventory. Apply retained `rls_statements` to the new static list: FORCE RLS, USING/WITH CHECK; SQLite keeps explicit tenant predicates. No new roles, global uniqueness, backfill or edits to migrations 1–40/replayed DDL. Existing enrollment is not registry approval.

## 2. Registration and evidence

Proposed grants: admin gets `MANAGE_AGENT_REGISTRY`; viewer/analyst/admin get `READ_AGENT_REGISTRY`. All writes require verified human OIDC, including owner/binding/permission changes. Creation requires an owner and binding. Active ↔ suspended is supported; terminal revoked is reserved for guarded 5.4. Registry suspension does not revoke vendor tokens.

Mutations require idempotency keys; edits also require expected revisions. Replay returns the original receipt; conflicting body/stale revision returns 409. Commit state and canonical before/after receipt atomically, with verified operator, reason and server time. Reuse evidence encryption/redaction; no tokens or backdating. Capture verifier issuer/subject/workload at the new boundary: current `Principal` loses some `AgentIdentity` fields.

Canonicalize with retained `domain/passport.canonical_bytes`; publish digests through `SqlTransparencyStore`; retry pending delivery after crashes, distinguish inclusion from external anchoring. `SqlSecurityAudit.record` swallows failures; the existing outbox requires incidents. Neither alone guarantees registry evidence. New records hold durable publication intent; retries may duplicate identical Merkle leaves, never logical changes. Administrative receipts cannot masquerade as execution receipts/Passports; keep that existing path for executions.

## 3. Identity contract and deterministic detection

An internal port accepts trusted, tenant-bound observations: platform/authority/account, stable event ID, occurrence/receipt times, actor identities, authentication/permission evidence and source digest. 5.1 uses fixtures; 5.2 supplies connectors. Telemetry cannot self-assert trusted attribution; targets are not actors. Missing source event IDs are explicit producer errors.

Official field checks below are dated **2026-11-12**; identifiers are opaque, case-sensitive strings, numeric IDs serialized losslessly. No prefix/name heuristic identifies an AI agent.

| Platform | Agent-like evidence, matching IDs and limitations |
|---|---|
| Google Workspace | `actor.applicationInfo.oauthClientId`, or token `activity` event parameter `client_id`, identifies an acting OAuth client. Preserve `actor.profileId`/`email` separately as the reported user. Consent `authorize/request/revoke` is not proof of app execution. [Reports Activity][g1] and [Token events][g2], checked 2026-11-12. Service accounts use IAM `uniqueId`; `email` and `oauth2ClientId` require an evidenced alias relationship. `callerType=KEY` alone is ambiguous, not a service-account classifier. [IAM resource][g3], checked 2026-11-12. |
| GitHub | `actor_is_bot=true` with `actor_id` identifies a bot; `actor`/bot login is display text. A bare `oauth_application_id` does not establish actor versus target: app-only attribution stays unknown pending the field-semantics question below. [Audit event fields][gh1], checked 2026-11-12. REST app `id`, installation `id`/`app_id`, `client_id` and `permissions` are distinct; scope bindings to the organization/installation and retain resource limits. Do not equate an audit OAuth ID to an App ID without evidence. [Apps REST][gh2] and [Users REST][gh3], checked 2026-11-12. |
| Slack | Nonempty `context.app.id` identifies the acting app; alternatively join `actor.user.id` to source-backed user metadata with `is_bot=true`. Audit `actor.type` remains user; `entity.app` is a target, not sufficient attribution. Preserve workspace/enterprise scope. App and bot-user IDs are separate bindings; do not invent prefix conversions. [Audit guide][s1] and [User object][s2], checked 2026-11-12. |

For each evidenced agent-like identity **K**, select the registry snapshot effective at the event time and match its complete typed key. **No binding → `UNREGISTERED_AGENT`**, informational review finding: “observed application/bot/service account has no registered binding”; it does not claim maliciousness or prove AI use. Matching suspended/revoked agent or retired binding → `INACTIVE_AGENT_ACTIVITY`; active binding → no registration finding. Missing IDs, ambiguous aliases, missing type proof or uncertain event time produce an explicit coverage gap, never a clean bill of health or guessed match. Google service-account attribution needs source-backed type/alias evidence; an email suffix alone is insufficient.

Dedupe receipts by `(tenant, platform, authority, account, source_event_id, actor_slot)`; a slot is a stable source-field pointer, even without an identity. Conflicting payloads are refused. Findings aggregate by `(tenant, rule/version, actor_key)`; gap keys instead use event/slot and appear under `GET /v1/registry/findings?kind=coverage_gap`. Count only distinct receipts under concurrent replay. Late events update historical findings using historical revisions; registry edits never erase them. Expose current registration separately; later approval prevents future drift, never retroactively excuses it. Wrong actor/type/alias attribution is a false positive; legitimate unregistered automation is still a registration gap. No name/vendor exemptions or claim that candidates prove AI use.

## 4. Scope drift

For a resolved identity, let **U** be permissions evidenced as used and **A** its approved set at event time. `U − A ≠ ∅` produces `SCOPE_DRIFT`, carrying the excess tuples, source receipt and approval revision; dedupe per identity/rule, retain each distinct excess in receipts. Unknown permission evidence yields `coverage=unknown`, not an empty U. Grant snapshots are labelled granted, never used: Google's token `authorize.scope`, GitHub installation `permissions`/audit [token scopes][gh4], and Slack `context.app.scopes`/`scopes_bot` do not establish which permission a particular action exercised ([Google][g2], [GitHub][gh2], [Slack][s1]; checked 2026-11-12). These sources alone cannot guarantee usage-drift coverage; no guessed action-to-scope mapping in 5.1.

## 5. Interfaces

All routes require authentication and tenant from `Principal`, never the body; cross-tenant IDs return 404.

| Proposed route | Capability |
|---|---|
| `GET /v1/registry/agents`, `GET /v1/registry/agents/{id}` | READ_AGENT_REGISTRY |
| `POST /v1/registry/agents`, `PATCH /v1/registry/agents/{id}` | MANAGE_AGENT_REGISTRY + human OIDC |
| `GET /v1/registry/findings`, `GET /v1/registry/records/{id}` | READ_AGENT_REGISTRY |

Plural reads use cursors. CLI `registry register/show/list/edit/suspend/resume/findings/receipt` uses these routes. Existing enrollment/grant CLI stays unchanged. SDK wrappers reuse `sdk/remote.py`, standard-library only. No console or public trusted-observation submission route.

## 6. Demo obligations

| Question | Evidence-backed answer |
|---|---|
| 1 — Which agent acted? | Typed observed identity → binding → stable registered agent ID/name, with source receipt and historical revision; unmatched is explicitly unregistered. |
| 2 — Which identity authenticated? | Retained verified issuer/subject/workload for Sentinel calls; platform-reported authenticated actor/app for audit observations, labelled with that assurance boundary. A registered alias or shared API key alone cannot prove the acting agent. |
| 3 — Who delegated? | 5.1 preserves authenticated operator and grant provenance; 5.6 must join an authenticated, explicit delegation issuance to retained execution authorization/approval and resulting receipt. Owner, approver and delegator are distinct. Existing `on_behalf_of`/`act` or Passport chain shape alone is insufficient; unsupported chains remain unknown. No restoration of A2A. |
| 4 — What permissions were granted? | Show registry-approved platform permissions, separately sourced platform-granted permissions, and retained local tool/execution authorizations at the relevant revision. Missing platform grants remain unknown; approval intent is not proof of a vendor grant. |

## 7. Fixture-only test plan

SQLite and real local PostgreSQL, no live platform calls: fresh 1→41 and 40→41 upgrades preserve old schema/data/indexes/policies/roles; new tables enforce RLS with a non-superuser role, including raw-SQL reads/writes, cross-tenant FKs and pooled-connection reuse. Cover every route's 401/403/404 and capability matrix, human-owner validation, revision races, tombstones, tenant-key collisions, replay/conflicting payloads, late events and canonical receipt tampering. Crash before commit leaves neither state nor receipt; crash during publication remains pending/retryable without duplicate changes.

For each platform, pair missing-binding detection with an exact active match; swap tenant/authority/account/kind/ID to make detection fire again. Human-only, target-only, malformed and unauthenticated observations must not become attributed agents. Drift fixtures use a strict approved subset, add/remove one evidenced used permission to toggle the finding, and prove grant-only or missing evidence cannot claim usage. Suspend/resume toggles inactive activity. Q1/2/4 fixtures must fail on forged identity links or altered grant provenance. Keep existing core assertions and the thin-SDK import probe unchanged.

## 8. Boundaries and approval questions

Excluded: connectors/enrichment (5.2), broader rules/permission mappings (5.3), vendor revoke (5.4), console/timeline/triage (5.5), demo/delegation completion (5.6), auto-enrollment and AI inference. Reviewed archived `platforms/{github_discovery,slack_apps,identity_agents,discovery_support}.py`: bounded paging, host-bound credentials and HTTP-200 `ok:false` remain references; discovery contracts/keyword scoring stay parked.

1. Approve coverage of **all evidenced apps/bots/service accounts**, including conventional automation, rather than an unsupported AI-only claim?
2. Approve **human-OIDC-only administration and OIDC-referenced human owners**, or require an accountable API-key-only onboarding alternative?
3. Accept honest **unknown usage scopes** where audit logs expose only grants? Which fixture-supported usage evidence should 5.2/5.3 add first?
4. Before connector implementation, confirm Google service-account attribution and GitHub audit OAuth-ID actor/target semantics and App/installation relationships with official field semantics and representative fixtures; no crosswalk is assumed here.
5. For Q3, approve a first 5.6 demonstration of explicit human→agent delegation backed by retained authorization/receipt evidence; multi-hop authority verification needs a separately approved contract.
