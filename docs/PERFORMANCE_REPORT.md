## Ingest p95 under concurrent load (2026-08-19) — METHOD CHANGED, READ THIS FIRST

Command: `PYTHONPATH=. python scripts/run_ingest_loadtest.py --workers 6 --events 55000`
Raw: `archive/pre-cleanup:docs/ingest_loadtest_postgres.json`

### Why the previous two numbers are withdrawn

This row has carried two figures, and **both were confounded**:

| Reported | Harness | Actually measuring |
|---|---|---|
| 624 ms | SQLite, in-process `TestClient`, 6 **threads** | unknown mixture |
| 995 ms | PostgreSQL, in-process `TestClient`, 6 **threads** | unknown mixture |

The PostgreSQL run's own statement breakdown is what disqualified it: only
**22%** of request latency was inside the database, and the single slowest
statement was `SELECT set_config('sentinel.tenant_id', …)` at **20.3 ms mean** —
a statement that touches no table and returns no rows. That is not database
cost. It is six Python threads contending for one GIL, with the load generator
competing against the request handler *inside the same interpreter*. The SQLite
figure had the identical flaw and nobody noticed, because it was never broken
down.

### The new method

- the application is a **real uvicorn server in its own OS process**;
- load is generated by **N separate OS processes**, each with its own GIL and
  its own keep-alive TCP connection (`scripts/loadgen_client.py`);
- requests cross **real TCP**, so sockets and HTTP framing are in the number;
- percentiles are computed over the **merged per-request latencies from every
  worker**, not averaged from per-worker percentiles, which is a different and
  wrong statistic.

### The attribution — corrected twice, and the second correction is the finding

> **Both earlier attributions in this section were wrong.** They are shown here
> rather than deleted, because the sequence is the point: an A/B is only worth
> what its control is worth, and I published two of them before checking that
> only one variable had moved.
>
> 1. *"GIL contention explains the miss."* Explained ~23%.
> 2. *"96% of the remainder is the classifier."* **Not supported.** The
>    classifier measures **0.69 ms p50 / 1.84 ms p95** in isolation and cannot
>    produce a 700 ms delta. Running the **shipped** process model
>    (`--server-workers 4`, matching the Dockerfile's `gunicorn --workers 4`)
>    moved nothing: 277.6 ms vs 274.1 ms, 87.2 vs 86.8 rps — so the cost was
>    never GIL-held either.

**What was actually happening.** `SoftAugmentedPolicy` classifies the
tool-call `action` field when an event has no `metadata.prompt`. The load
generator's default action, `read_file`, scores **0.5409** — above the 0.5
threshold. So with detection enabled, **every single request fired an incident**
and wrote rows to `incidents`, `incident_transitions`, `domain_events`,
`work_queue` and `outbox`. The A/B compared *"an incident per request"* against
*"no incidents at all"*.

Four runs, 8,000 rows, 6 writers, back-to-back on an otherwise idle machine:

| Action sent | Detector | p50 | p95 | throughput |
|---|---|---|---|---|
| `read_file` (**fires**, 0.5409) | on | 36.70 ms | **274.07 ms** | 86.75/s |
| `read_file` | off | 18.09 ms | 25.41 ms | 289.22/s |
| `list_dir` (benign, 0.3502) | on | 28.46 ms | **37.71 ms** | 193.06/s |
| `list_dir` | off | 20.89 ms | 29.71 ms | 252.92/s |

| Attribution | Δ p95 |
|---|---|
| **The classifier itself** (benign action, no incident written) | **+7.99 ms** |
| **Incident creation** triggered by the false positive | **+236.36 ms** |

**So the detection-quality defect and the latency defect are the same defect.**
F-10 in `docs/THREAT_MODEL.md` records that the classifier fires on **51.7% of
ordinary tool-call actions** (31 of 60). Each false positive is a full incident
write. Fixing F-10 removes the great majority of this row's cost; tuning the
classifier's inference speed would recover about 8 ms.

`--action` is now a first-class option on both the driver and the load worker,
with the scoring consequence documented at the definition site, so a future
measurement cannot silently change what is being measured.

### RESOLVED 2026-08-19 — 786.0 ms → 37.99 ms

The row passes. The cause was never the database, the harness or the classifier's
inference cost: it was **F-10**, the detector firing on 51.7% of ordinary tool
calls, each false positive writing a full incident across four tables.

Same command, same payload, same 55,000 events, before and after removing the
`action` fallback:

| | before | after |
|---|---|---|
| p50 | 75.71 ms | **28.40 ms** |
| **p95** | **786.02 ms** | **37.99 ms** |
| p99 | 2230.09 ms | 68.57 ms |
| max | 5951.55 ms | 100.95 ms |
| mean | 190.66 ms | 29.21 ms |
| throughput | 30.77 req/s | **191.32 req/s** |
| **`incidents` written** | **56,796** | **0** |
| `incident_transitions` | 56,796 | 0 |
| `domain_events` | 56,796 | 0 |
| `work_queue` | 56,796 | 0 |
| non-2xx / transport errors | 0 / 0 | 0 / 0 |
| **vs `< 500 ms`** | **FAIL** | **PASS** |

**The census is the proof of mechanism.** A latency improvement alone would be
consistent with several explanations; 56,796 spurious incidents becoming 0 is
consistent with one. And it cost no detection: recall on the real test set is
**0.8545, unchanged**, because the removed feature never carried signal — the
same action string appears under both labels in the corpus.

### The measurement that made this findable

### The gate number, with the database state recorded

"p95 at 55k rows" was ambiguous until the census existed, because *which* rows
depends on whether the detector fires. Two runs, both 55,000 seeded events,
6 writers, detector on, 1,800 measured requests:

| | **Worst case** — every event fires | **Benign** — no event fires |
|---|---|---|
| Action sent | `read_file` (0.5409, above threshold) | `list_dir` (0.3502) |
| `incidents` | **56,796** | ~0 |
| `incident_transitions` | 56,796 | ~0 |
| `domain_events` | 56,796 | ~0 |
| `work_queue` | 56,796 | ~0 |
| p50 | 75.7 ms | 40.5 ms |
| **p95** | **786.0 ms** | **58.1 ms** |
| p99 | 2230.1 ms | 90.1 ms |
| max | 5951.6 ms | 122.2 ms |
| throughput | 30.8 req/s | 134.3 req/s |
| non-2xx / transport errors | 0 / 0 (all 1800 were 202) | 0 / 0 |
| **vs `< 500 ms`** | **FAILS** | passes |

**These are two different workloads, not a range**, and neither alone is the
production number. What decides where a real deployment sits is the **rate at
which the detector fires** — and F-10 measures that at **51.7% on ordinary
tool-call actions**, which places production much nearer the failing column.

That is why the gate row reads `fail` at 786.0 ms: it is the honest worst case
for a system whose detector currently fires on half of routine traffic.

### What this number is NOT

- **One host, loopback TCP.** No network latency, no load balancer, no ingress,
  no TLS termination, a single replica, no competing tenants. All are real
  sources of production latency this cannot see. What was removed is one
  specific, *measured* confound — not all of them.
- **The 31.3 ms row is attribution, not a gate result.** It comes from a run
  that was discarded for not being comparable (it disabled the detector while
  the run it was being compared against did not). It is valid as a one-variable
  contrast and is labelled as such.
- **The seed-phase throughput in the raw JSON (28.79 req/s) is contaminated** —
  seeding overlapped a DR drill running concurrently on the same machine. The
  *measure* phase ran alone afterwards, so the p95 above is clean. Quote the
  p95; do not quote that seed rate.

### A defect found in this harness, recorded rather than quietly fixed

The first version of the script reported `rows_in_incidents_after: 0` for a run
that had just written 54,996 rows. The count was an unscoped
`SELECT count(*) FROM incidents` against a table under `FORCE ROW LEVEL
SECURITY` using the non-superuser app role — so it returned a confident zero.
That is the **identical defect as the retention sweep**, written in the same
session that documented that class four times over. Fixed by setting the tenant
context, and the code carries a comment saying so.
