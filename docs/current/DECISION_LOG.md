# Decision log: fail-closed exceptions

Sentinel's stated default is fail closed: when a control cannot decide, the action does not proceed. Every place where the code deliberately departs from that default is an exception, and this log is where each one is recorded, owned, bounded and reviewed.

This is a product document. The entries below were read from the code on 2026-09-14 (branch `program/production-readiness`) and each cites the file that implements it. Where a column is not knowable from the code (owner, customer approval, observed usage) the entry says so instead of guessing.

## Rules for this log

1. An exception is any code path that allows an action, a request or a decision to proceed when the control that should have decided it was unavailable, disabled or skipped.
2. Every exception has an owner, a scope, an expiry and a compensating control. An exception with no expiry is a design decision, and must be re-justified at the quarterly review in `RELEASE_GOVERNANCE.md`.
3. "Customer approval" records whether a customer must consciously opt in (a configuration value they set, a client flag they pass) or whether the exception is active without their knowledge. The second kind is the one to remove first.
4. "Observed usage" is measured, never estimated. Until a design partner runs Sentinel against real traffic, the honest value is "no production data".
5. A new exception may not ship without a row here. A row here may not be closed without the code change that removes it and the file path that proves it.

## Columns

| Column | Meaning |
|---|---|
| id | Stable identifier, `FCX-nnn` |
| control | The control that is bypassed or degraded |
| exception | What the code does instead of failing closed |
| why | The reason recorded in code or design |
| owner | Person accountable for the exception (role until named) |
| scope | Which deployments, modes and call paths the exception affects |
| expiry | Date or condition after which the exception must be re-justified or removed |
| compensating control | What makes the exception visible or bounds its damage |
| metric | The number that shows how often the exception is exercised, and its data source |
| customer approval | Whether the customer must opt in, and how the opt-in is recorded |
| observed usage | Measured frequency, with period and source, or "no production data" |

## Exceptions that do not exist, and should stay that way

Recorded so that a future change adding one is a visible diff against this list.

- `SentinelClient.execute` has no fail-open mode (`sentinel/sdk/remote.py`).
- The MCP wire proxy refuses unknown or blocked servers before any network activity (`sentinel/interface/mcp_proxy_routes.py`).
- The transparency root is reported `independently_verifiable: false` until published to a sink outside the operator's control; the proof is still served, with the limit stated (`sentinel/interface/transparency_routes.py`).
- `passport-create` does not exist as a CLI command (`sentinel/interface/passport_cli.py`).

## 2026-09-17 supported-chart restrictions

The candidate Helm chart refuses FCX-001 fail-open=true and FCX-005 binding=false, and explicitly enables enforcement rather than the advisory default in FCX-004. The underlying compatibility settings still exist outside this declared topology; no customer exception is approved by these changes. Local schema/parser tests establish configuration behavior only.

Operational trace delivery is intentionally lossy and does not authorize an action or satisfy an audit/receipt gate. A collector outage drops bounded spans, increments `sentinel_trace_spans_dropped_total{reason="export_failed"}` and is alertable. Queue and shutdown loss have separate fixed reasons. Engineering owns this telemetry trade-off; review by 2026-10-15 before pilot admission. Production usage and customer acceptance remain unobserved. Durable evidence failures retain their fail-closed/unknown-outcome execution semantics.

## 2026-09-19 image gate correction

The historical automatic exception for unfixed HIGH/CRITICAL image vulnerabilities is removed from both the local gate and configured CI. There is no customer-approved or executive-approved vulnerability waiver in this program. Missing upstream fixes do not authorize release. R-015 remains open; sanitized evidence retains both fixed-available and unfixed findings. GitHub Actions was not executed during the requested hold.

## 2026-09-20 conflict responses are recorded failures

A definitive 4xx from a target (a Kubernetes 409 on the approved resourceVersion, a 403, a 422) is now recorded as a FAILED operation instead of `unknown_after_effect`. This narrows the conservative rule adopted on 2026-09-19: the server's answer is proof that nothing was admitted, and sending definitive conflicts to a human trains operators to dismiss the unknown state. A 5xx, a timeout and a lost response remain unknown. The adapter must raise `ToolAdapterRejectedByTarget` only after receiving such a response; `tests_arch/test_kubernetes_outcome.py` holds both directions.

## 2026-09-20 owner decisions: streaming and containment governance

Decided by the owner. (1) MCP notifications may be relayed incrementally. The earlier guarantee that no streaming handle escapes `outbound.py` is kept in a narrower form: callers receive bounded byte strings per event, never the socket. This is not a fail-open exception: a refused notification is dropped, the final result is inspected as before, and server-initiated requests are refused outright. Trade-off accepted: a dropped notification is silent to the client and visible only in the audit row. (2) A containment cannot be activated without a reason of at least 8 characters and an expiry at most 30 days out. This tightens, and needs no exception row. Review both by 2026-10-31 or at the first design-partner deployment, whichever is sooner.
