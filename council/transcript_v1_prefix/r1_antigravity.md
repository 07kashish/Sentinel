## Verdict in one paragraph
Sentinel SOC is a functionally hollow hackathon artifact masquerading as a production-grade enterprise AI security platform. While it successfully implements a multi-agent orchestration pipeline (`api/main.py`) and genuinely executes on-chain transactions to the Base Sepolia testnet (`agents/attestation_agent.py`), the core premise collapses under scrutiny. Its threat detection relies entirely on trivially bypassed regex and substring matching (`app/monitoring/rules.py`, `app/normalizers/prompt_events.py`), its entire incident registry is an ephemeral in-memory dictionary that wipes on restart (`api/store.py`), and its accuracy framework grades its own homework by hardcoding expected outcomes against a frozen mock dataset (`evaluation/metrics.py`). Operating in a rapidly consolidating market dominated by heavily funded incumbents like Palo Alto and Check Point, Sentinel currently offers no defensible moat, no persistent product, and an architecture fundamentally unsuited for enterprise scale.

## Strongest thing in this codebase
The strongest element is the multi-agent orchestration pipeline found in `api/main.py` (lines 125-301) and the functional blockchain attestation implementation. The pipeline effectively coordinates specialized LangChain agents (`agents/supervisor_agent.py`, `agents/investigation_agent.py`, `agents/evidence_agent.py`) to triage, enrich, and attest to incidents autonomously. Crucially, the on-chain attestation is not a fake stub. In `agents/attestation_agent.py` (lines 64-103), the code genuinely utilizes `web3.py` to construct, sign, and broadcast an Ethereum transaction to the Base Sepolia testnet using a real contract ABI, provided `DEPLOYER_PRIVATE_KEY` and `CONTRACT_ADDRESS` are supplied. It accurately bridges agent logic with cryptographic finality, proving the team can ship complex, multi-stage, cross-domain workflows.

## Most serious defect
The total absence of data persistence destroys the core value proposition. In `api/store.py` (lines 14-16), the entire state registry is defined as a simple in-memory dictionary: `_store: Dict[str, dict] = {}`. When the application crashes or restarts, all incident history, metrics, and runtime state are permanently deleted. For a product positioning itself as a "tamper-proof incident attestation layer," losing the underlying payload data that contextualizes the blockchain hashes renders the on-chain cryptographic proofs entirely useless. Furthermore, `synthesis_credentials.json` (lines 1-7) commits a live `sk-synth-...` API key directly into the repository. This represents a catastrophic operational security failure for a cybersecurity company.

## Docs vs reality
- **Claim:** The YC Application Notes claim Sentinel provides "Detection for prompt injection and sensitive file access."
- **Reality:** The codebase uses literal string matching, not AI, for detection. `app/normalizers/prompt_events.py` (lines 8-13) relies on naive `re.search` for exact strings like `ignore previous instructions`. `app/monitoring/rules.py` (lines 12-14) uses Python's `in` operator to check if `/etc/passwd` or `rm -rf` are present. This is hardcoded keyword matching dressed up as AI detection.
- **Claim:** The README claims an "Evaluation / Metrics & Accuracy Framework."
- **Reality:** `evaluation/metrics.py` (lines 66-77) hardcodes `EXPECTED_ANOMALIES = 7` and `EXPECTED_NORMAL = 3`. It evaluates itself against a static 10-event array in `simulation/demo_events.py`, generating fake accuracy percentages based on self-defined synthetic homework.
- **Claim:** "Continuous Monitoring: Polling real-time event sources" (README).
- **Reality:** There is no continuous polling mechanism for real-time sources. The system simply exposes static POST endpoints in `api/main.py` (lines 486-555) that wait passively for payloads. Authentication is limited to a single, global `SENTINEL_API_KEY`, lacking any sophisticated identity binding or multi-tenancy.

## Detection quality vs OWASP ASI Top 10
Sentinel's detection logic provides the illusion of security but offers zero realistic protection against modern threats. 
- **ASI01 Agent Goal Hijack (Prompt Injection):** "Covered" via regex matching in `prompt_events.py`. In reality, the false-negative rate on real traffic will be near 100%. Sophisticated zero-click prompt injections (like the EchoLeak vulnerability cited in the brief) do not use literal strings like "ignore previous instructions".
- **ASI02 Tool Misuse & ASI05 Unexpected Code Execution:** "Covered" via basic substring checks for `curl`, `wget`, or `wallet.json` in `app/monitoring/rules.py`. A real attacker will simply use aliases, hex encoding, or symlinks to achieve a 100% evasion rate.
- **ASI03 Agent Identity & Privilege Abuse:** Not covered. Identity is self-reported as a plain string (`agent_id`) in the API request, completely ignoring the industry shift toward PKI-based or OAuth identity for MCP servers.
- **ASI04, ASI06, ASI07, ASI08, ASI09, ASI10:** Completely unaddressed by the codebase.

The realistic false-positive rate will also be unmanageably high, as any legitimate developer discussion or tool invocation containing the word "secrets" or "override" will trigger critical alerts, exhausting SOC analysts.

## Product thesis (or the case against one)
There is no viable commercial product here. To sell an "observe mode" solution, the absolute minimum requirement is persistent, searchable, and irrefutable audit logs. Because `api/store.py` wipes state constantly, this fails the minimum viability test. To sell a "protect mode" solution, the detection engine must be robust against evasion; Sentinel's static keyword matching fails instantly. The on-chain attestation feature, writing per-event hashes synchronously to Base Sepolia, introduces severe latency bottlenecks and exposes metadata to a public ledger�something no enterprise security team will accept. Nobody will pay for an in-memory SIEM with regex rules and public testnet blockchain writes.

## Company verdict
A company cannot be built on this codebase. The capital required to build a persistent, multi-tenant backend, train semantic detection models, and develop deep integrations with enterprise MCP servers is immense, and Sentinel is starting from zero in a market that saw $29B in M&A activity in 2026. The founder's wedge (a 7-day assisted pilot) will fail immediately once a prospective client realizes the dashboard resets if the server restarts. Addressing the on-chain attestation directly: it is a pure hackathon artifact. Writing high-volume security logs synchronously to a blockchain�even a Layer 2 testnet�is an architectural anti-pattern. The mainstream enterprise standard is hybrid: maintaining hash-chained Merkle trees locally and periodically anchoring the root hash to a chain. Sentinel's per-event write model is both fundamentally unscalable and unserious to a CISO. The single biggest reason this fails is that it is a toy architecture competing in an institutionalized market.

## Top 5 gaps, ranked
1. **Complete Lack of Persistence:** The state is stored in an ephemeral Python dictionary (`api/store.py`). Real-world operational resilience is impossible without a persistent database.
2. **Naive Detection Engine:** Relying on `re.search` and basic substring matching (`rules.py`, `prompt_events.py`) provides zero defense against polymorphic prompt injection or obfuscated tool abuse.
3. **Absence of Identity and Authentication:** The system relies on self-reported agent IDs and a single static API key (`api/main.py`), ignoring the critical need for PKI-based agent identity (ASI03) and multi-tenancy required for SaaS operations.
4. **Unscalable Attestation Architecture:** Synchronous, per-event writes to a public blockchain (`agents/attestation_agent.py`) will instantly bottleneck the ingestion pipeline under production load.
5. **Fraudulent Evaluation Metrics:** The accuracy framework (`evaluation/metrics.py`) is entirely synthetic, hardcoding the expected results for a static 10-event demo file rather than evaluating against a dynamic, adversarial benchmark.
