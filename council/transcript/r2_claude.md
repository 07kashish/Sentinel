## Where a peer is right and I was wrong

**Codex — the "esc() escapes every server-supplied value" claim is false, and I did not catch it.** Remediation claim #2 says the escaper now covers every server value. It does not. `dashboard/index.html:1349` interpolates `JSON.stringify(inc.intel.external_data, null, 2)` straight into `innerHTML` with no `esc()`, one line below indicators that *are* escaped (`:1348`). `JSON.stringify` escapes quotes and backslashes but not `<`, `>`, `&`, so an `external_data` value of `</div><img src=x onerror=…>` in attacker-controlled threat-intel renders live. `:1270–1274` injects `transaction_hash` into an `href`, `title`, and text node unescaped. This is the **sixth instance of the repository's signature pattern**: a fix closed the demonstrated sink (`raw_payload.content`) and the *claim* generalised to "every value" while a sibling sink stayed open. Credit to Codex; this is verifiable and I should have found it in my own code.

**Codex — the terminalisation path reintroduces an unfenced write.** Confirmed structurally: `_terminalise` (`api/pipeline.py:617`) calls `repository.fail()` with no epoch; `fail()` defaults `epoch=None` (`repository.py:652`); `transition`→`_locked_incident` skips the fence entirely when epoch is None (`repository.py:289`). The module's own docstring (`pipeline.py:45–50`) asserts "There is no direct `repository.transition(...)` call in this module: a helper that can be called without the epoch is a call site that will eventually be called without it." `_terminalise` is exactly that helper, in the same file, in the error path. The invariant is violated by the code that documents it.

## Where a peer is wrong

## Component-by-component contest

**1. Lifecycle / execution fence.** Strongest claim (Antigravity): "completely closing the concurrent update race conditions" (Engineering 85). My challenge: not complete — the terminal error path is unfenced. **Problem:** a worker that lost its lease can still write `FAILED`. **Evidence:** `pipeline.py:617` → `repository.py:652,289`. **Risk:** a stale worker terminalises an incident a new owner is legitimately advancing; the harm is *bounded* because terminal errors are deterministic and both workers resume from the same durable rank, so outcomes usually converge — but the stated "no unfenced write" invariant is false, and that is what the mutation harness is supposed to protect. **Solution:** thread `epoch` through `fail()`/`_terminalise`; make the worker-path failure API require it. **Tradeoffs:** none material. **Effort:** 1–2 days + a concurrent fault-injection probe. **Priority:** High (not Critical — Codex over-rated; deterministic convergence caps blast radius).

**2. Attestation / outbox (H-4).** Strongest claim (mine, in remediation): claim→publish→record with idempotency key closes double-anchoring. My challenge: the idempotency key is generated and stored but **never passed to the gateway**. **Problem:** lease-steal during the external-call window re-anchors. **Evidence:** `pipeline.py:405–409` calls `publish_attestation(detection, evidence, subject_address=…)` — no key; if A claims (epoch 5), B steals (epoch 6), A publishes then fails `complete_attestation` at `:617` (FenceLost), the outbox stays `delivering`, and B re-enters `claim_attestation`, sees non-`delivered`, and publishes again. `assert_execution` (`repository.py:251`) exists *precisely* for "abort before a side effect" but is not called before publish. **Risk:** duplicate on-chain writes; testnet-bounded today, real once anchoring hits a paid chain. **Solution:** call `assert_execution` immediately before publish; pass `idempotency_key` to the gateway; reconcile a receipt before re-publish. **Tradeoffs:** requires a gateway that honours idempotency. **Effort:** 1–2 weeks. **Priority:** High.

**3. Dashboard / XSS.** Resolved against my own remediation (above). **Solution:** `textContent` for `external_data`; build the basescan link via a validated `URL` and DOM node; the CSP still allows inline script, so add nonces. **Effort:** 2–4 days. **Priority:** Critical — it is stored XSS in the analyst console, and the *claim* that it was fixed is what makes it dangerous.

**4. Detection / eval.** Both peers converge (AI/ML 17 / 45). My position: Codex's 17 is right, Antigravity's 45 is charity. AUC 0.763 two-fold, ECE 0.48, unchanged across eight passes, classifier demoted to shadow (`app/monitoring/rules.py`). **Risk:** the product's *named* value — detecting the attacks in §1 — is the one thing that did not move. **Priority:** this is the constraint, and it is not an engineering fix; it needs partner telemetry. No score should rise here.

**5. Provenance / verify_package.** Strongest claim (Antigravity): fail-closed, cannot forge. Largely holds — v2 manifests bind tenant+incident (`pipeline.py:305–312`), verify requires an out-of-band signer. My challenge is narrower: the redaction correlation hash is unsalted SHA-256 (Codex, `redaction.py:53–69`), so low-entropy bodies are re-identifiable — a GDPR purpose-limitation snag, not a forgery. **Solution:** tenant-keyed HMAC. **Effort:** 2–3 weeks. **Priority:** High for any regulated pilot.

**6. Mutation harness.** Both credit it as real (it loads a mutated module and requires a red probe). My challenge answers the brief's dare directly: **the harness would not catch the `fail()`-epoch=None mutation**, because no probe asserts terminalisation is fenced. The harness proves the *guards it enumerates* are load-bearing; it says nothing about invariants no probe encodes. That is not theatre, but it is a narrower guarantee than "the other fixes are trustworthy."

## What ALL of us missed entirely

The repository is **not under version control and has no durability floor** — the brief's own §8.1 records that `api/pipeline.py` and `app/core/dlq.py` were found at 0 bytes, `.pyc` recompiled over the truncation, unrecoverable. Every seat scored the *code*; none scored the *operation that produces the code*. For a company whose entire pitch is tamper-evident, non-repudiable audit trails, the fact that its own source can be silently destroyed with no git, no CI signal until collection fails, is a diligence red flag about the team's engineering discipline that outweighs any single bug. A $100M buyer diligences the SDLC, not just the tree. That belongs in the Engineering and Investment scores and none of us priced it.
